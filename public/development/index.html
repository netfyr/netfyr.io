Development lifecycle

Last reviewed 23 October 2026 · Edit this page

Start here

A spec defines the behavior to build and the checks it must pass. Link code, tests, review, and documentation to the applicable spec.

  1. Read the project philosophy and the target repository's contribution guide. For core, start with Contributing to netfyr.
  2. Find a task on the spec board or planning page. Check its dependencies and implementation assignment, and coordinate with its owner before starting.
  3. Read the applicable merged spec in netfyr/specs. If the behavior is unclear or a prerequisite is missing, raise that in the spec discussion.

Contributions also include reproducing bugs, reviewing specs, improving examples, and correcting documentation. Use the relevant repository's issue or pull request discussion to explain the problem and agree the scope.

The merged spec is the implementation acceptance baseline. A live board note can contain a newer revision still under review. Follow revision and replacement links before relying on an older requirement.

Development lifecycle

  1. Propose the behavior

    Create a spec using the board's template. Describe the problem, scope, dependencies, acceptance scenarios, numbered requirements (FR-nnn), and measurable success criteria (SC-nnn). Top-level specs define principles inherited by feature specs.

  2. Review and approve the spec

    Move the draft to ready for review. Discuss comments and accept or reject suggestions in the editor. Authorized approvers approve through the editor controls; the current roster and quorum live in roles.yml.

    Once approval and discussion checks pass, SpecDoc opens a publication PR in netfyr/specs. Spec content is reviewed in SpecDoc; contributors do not edit the published files or repeat the review in GitHub.

    Automatic merging by the publication bot is still pending. Approval alone does not publish the spec; use the merged Git revision as the implementation baseline.

    Maintainers handle onboarding, access and repository or bot configuration through reviewed GitHub PRs. This includes roles.yml changes to reviewer eligibility, quorum or the feedback-bot selection.

  3. Implement and verify

    Work against the merged requirements and implemented dependencies. Keep each feature PR focused on one governing spec. Build in reviewable increments, map tests to acceptance scenarios, and report a missing dependency instead of silently taking over its implementation.

  4. Review and merge the code

    Submit the behavior change, test evidence, documentation, and known limitations together. Address review findings and rerun the affected checks. Preserve the spec references when merging so the resulting history records what shipped.

  5. Record completion

    When the completing commit reaches a configured implementation repository's default branch, SpecDoc detects its implements reference and marks the feature implemented. Partial work does not claim completion. Top-level principles remain approved; they are not closed as implemented.

    If implementation reveals a requirement that needs changing, revise the spec through review. Corrections retain its identity and path; a replacement spec records what it supersedes. Update affected user documentation.

SpecDoc's review snapshots and diffs compare the text at status changes, approvals and publication. Spec checkpoints tag the merged specs at a fixed Git revision for a shared baseline.

Agents and automation

Reviewing a draft
When configured, SpecDoc's LLM review bots check drafts for unclear requirements, missing decisions and contradictions with approved top-level principles or selected related specs. They leave review comments in the editor; possible cross-spec conflicts appear as advisory findings on board cards.
Reconciling specs
A configured bot's checkpoint overlap review can flag duplicated responsibilities and incompatible requirements across approved specs. An agent can compare the cited requirements and draft a reconciliation. Agree which behavior should govern, then review changes to each affected spec. Record dependencies and replacements explicitly. When moving a requirement, check that the receiving spec actually covers it before retiring the old text.
Writing and reviewing code
Use coding agents to find relevant code, draft changes and tests, or review a patch against its spec. Give the agent the chosen merged spec revisions, inherited rules and dependencies. Review its diff and the actual check results before submitting; agent-written changes follow the same contribution rules.
Learning from implementation review
A configured feedback bot reads a linked, merged implementation PR's discussion and final changes, then proposes spec amendments in the editor. Accept or reject the suggestions through review. A code bug that violates a clear requirement calls for a code fix.
Routine automation

Repository hooks and CI run the checks configured for that repository.

SpecDoc opens publication PRs after approval and discussion checks pass. The publication step describes the remaining rollout requirement.

SpecDoc tracks implementation through merged Git references.

Model reviews cover limited context and can miss or misread a conflict. Check the cited text and any omissions. Contributors resolve findings; authorized reviewers approve the resulting specs in SpecDoc.

Working on code

For core development, use Linux, Git, a Rust toolchain supporting Rust 2024, and Make. Install pre-commit before setting up the repository hooks. Test-specific system dependencies are documented with their suites.

git clone https://github.com/netfyr/netfyr.git
cd netfyr
cargo build
make hooks

The core hooks check formatting on commits touching Rust and run Clippy before pushes touching Rust.

  • Use cargo fmt and keep Clippy clean. New crates inherit the workspace's shared metadata.
  • Prefer standard-library solutions. Justify external dependencies in manifest comments. For low-level networking, check the rust-netlink ecosystem, including rtnetlink, and Nispor before adding custom code, and explain any concrete API gap.
  • For user-facing work, consult the design library and project identity. Cite the applicable design rules and reuse shared components where available.

A requirement mismatch needs an explicit decision: correct the implementation or propose a spec revision. Keep unrelated cleanup in separate work.

Testing and evidence

Before submitting core changes, run the checks required by its contribution guide:

cargo test
make test
cargo fmt --check
make clippy

For a focused shell test run, make test TAGS=ipv4,routing selects either tag; make test TAGS=ipv4+routing requires both. A focused run does not replace the full pre-submission checks.

Pure logic
Place Rust unit tests beside the code in #[cfg(test)] modules. They should not need external tools, network namespaces, or built binaries.
CLI and system behavior
Shell tests live in tests/. Name them for the behavior, put tags within the first ten lines, keep helpers in tests/lib/, and locate built binaries through NETFYR_TARGET_DIR.
Regressions
Reproduce the bug with a test that fails for the reported behavior before applying the fix. Verify that it passes afterward. A compile failure does not reproduce a behavior bug.
Network changes
Verify results against the real kernel. The testing infrastructure spec defines pytest acceptance tiers and independent observations. Privileged candidate execution belongs in a disposable VM, with an outer snapshot and evidence retained outside the guest. Follow the suite instructions in the branch being tested.

Missing prerequisites must fail visibly. Share the exact commands, revision, environment, results, and any checks you could not run separately in chat or review evidence. A merged testing spec describes required behavior; it does not mean every harness is already available on the default branch.

Submitting a change

Use imperative commit subjects and explain why the change is needed. Each commit should be one reviewable increment. The pull request should explain the problem, resulting behavior, and material limitations.

The spec-reference rules use a Spec: trailer for work implementing a spec. Put its published path, without .md, in each contributing commit and at the end of the PR description. Put the qualified implements reference in both the completing commit and the completing PR description so SpecDoc can track completion and collect implementation feedback.

A proposed maintenance exception uses No-Spec: Fix README spelling without changing behavior for work without a related spec. It requires a concrete reason in each maintenance commit and in a maintenance-only PR; feature PRs retain their governing Spec:. This exception depends on the SPEC-009 amendment being published and the matching checker landing. Until then, the published spec-reference rules apply.

Spec: core/004-network-backend
implements netfyr/specs#17

This example refers to the backend spec: #17 is its original spec pull request number, not the 004 in its filename. Include both lines in the completing commit and PR description. Earlier or partial work carries only Spec:; maintenance commits never claim completion. A bare implements #17 would refer to the wrong repository.

  • For a regression with a known introducing commit, add Fixes: HASH12 ("COMMIT SUBJECT").
  • Update affected documentation. Add a core CHANGELOG.md entry under [Unreleased], with the spec path in parentheses, when users or packagers would notice the change.
  • Retain the references in the final merge or squash message. Check that the linked spec and completing reference describe the same work.

Spec-reference rules apply even when hooks and CI do not enforce them.

Tools and infrastructure

Hosted services and test machines have separate access arrangements.

Where to work and what access is needed
ResourcePurpose and access
GitHub Source, merged specs, issues, and pull requests. Public repositories can be read and cloned; use your GitHub account to contribute. Repository permissions govern review and merge access.
SpecDoc The spec board, editor, planning view, and dependency library. Public specs are readable without signing in. Sign in with GitHub to participate; approval rights come from the project's configured roles.
nm-devtools Shared scripts and workflows for development, bug reproduction, review, VM tests, and network transition experiments. These are optional tools; follow the target checkout's actual commands and contribution rules.
SpecDoc CLI Use the specdoc command to read specs, edit notes with conflict checks and submit bot reviews. The CLI guide covers installation, authentication and structured output.
SpecDoc MCP Optional context tools for agents: context, brief, search, get, neighbors and trace. Check freshness and truncation notices. History links help find requirements; they do not prove compliance. The read API supports other integrations.
testvm and vm-test Tools for configured libvirt test environments, snapshots, rollback, and evidence collection. Cloning the tools does not provision a VM or grant host access. Arrange shared-host access with its maintainer, or configure your own disposable environment.
Site hosting The website, user docs, and design library publish through GitHub Actions and Pages. Maintainers manage DNS and hosted services. Contributors can propose content changes through the site repositories without infrastructure credentials.

On a shared test host, claim a VM before a long run and release it afterward. Respect another session's lease. Preserve a recoverable snapshot and collect evidence before rollback; vm-test supports that workflow.

If you need access or cannot run a required check, explain the task and the missing capability in the relevant issue or pull request so a maintainer can help arrange it. Include what you have already verified.

Documentation and publishing

Keep documentation with its audience and source:

  • netfyr/specs holds the reviewed requirements.
  • netfyr/docs publishes user guides and configuration reference at docs.netfyr.io. Its README describes preview and validation commands.
  • netfyr/design owns the design library, shared assets, and component guidance.
  • netfyr/netfyr.io holds this contributor guide and the project landing page.

The docs repository pins the core revision used by its reference and example checks. Its scheduled update workflow proposes changes in a pull request after validation. Review the core changes, update affected guides, and merge the reviewed update to publish it.

Implementation completion, documentation publication, and a software release are separate events. A board card marked implemented means the completing commit landed. Core changes remain in [Unreleased] until released; this guide does not define a release cadence.

For SpecDoc service upgrades, follow its release and rebase guide, which covers editor and board images and updates to the HedgeDoc fork.

Keeping this guide current

Check repository instructions and merged specs when a command, role, or requirement changes. Confirm a tool is present in your checkout before using it.

Propose corrections through this page's source, with a link to the changed rule or implemented workflow. Keep new plans clearly identified until the corresponding tooling or service is available.
